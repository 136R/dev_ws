# 回复格式

## 说人话（所有回复都适用，比下面所有规则优先）

用户是这个项目的主人，但**不是这些技术领域的科班出身**。他看不懂的一句话，
哪怕内容全对，也等于没写。

1. **术语和缩写第一次出现，当场翻译。** 大白话在前，术语在括号里。
   - ❌「零偏超过阈值会导致 ZUPT 静默失效」
   - ✅「陀螺仪静止时也会报一个假的转速（叫"零偏"）。它太大的话，
     程序就永远认不出车是停着的，静止修正（ZUPT）等于没开，而且不会报错」

2. **能说现象就别说原理。** 先说"你会看到什么"，再说"为什么"。
   - ❌「yaw 会漂移」→ ✅「车明明停着，地图里的车头却在慢慢自己转」
   - ❌「TF 时间戳不单调」→ ✅「后来的数据带着更早的时间，下游直接不认」

3. **一句话只说一件事。** 超过 30 字或出现第二个「——」就拆成两句。
   不要用分号把三层因果串成一句。

4. **一段话里最多两个缩写。** 超了就把其余的换成中文说法。

5. **不算术语、照写不误的**：文件名、参数名、话题名、命令、数值。
   那是他要动手用的东西，删了他就没法操作。

6. **「为什么」写多深，看场景 —— 不是固定长度。**

   | 场景 | 写法 | 大致长度 |
   | --- | --- | --- |
   | 他要你修好某个东西、看报错、查日志 | 只写**你会看到什么** + **去哪改**。机器内部怎么回事不写 | 2–3 行 |
   | 他在做决定（选方案、定参数、判断值不值得改） | 把机理拆开写清楚 —— 他要靠这个判断你说得对不对 | 展开 |
   | 他明确问「为什么」 | 同上，展开 | 展开 |

   判不准时按短的写，他想深入会自己追问。

## 退化规则（先判这条，再看下面）

**纯事实问答不套任何结构。** 当答案是一个值、一个是否、一个位置、一条命令时，
直接一行答完就停 —— 不加粗结论行、不列要点、不给出处、不附验证命令。

出处只在两种情况补：用户追问，或答案本身反直觉（与用户明显的预期不符）。

```
问：EKF 频率是多少？
答：100 Hz。                              ← 对
答：**EKF 跑 100 Hz。** - `ekf_hw.yaml`…  ← 错，纯膨胀
```

下面的结构化格式**只在产生改动或做出判断时启用**。

## 结构化格式（产生改动时）

1. **首行一句加粗结论** —— 做了什么 / 答案是什么 / 为什么不做。
   这一行**不许含未解释的术语**，外行读一遍就要能懂。
   结论不许出现在第二段之后，不许先铺垫背景再给结论。

2. **要点列表，每条必须带出处或落点。**
   - 出处 = `` `文件名` 的 `键名/符号名` ``（不写行号，行号会漂）
   - 落点 = 可直接执行的命令、可直接打开的路径、可直接改的键名与目标值
   - 只有判断没有落点不合格：「建议调大一点」→ 写成「`laser_filters.yaml` 的 `lower_threshold` 调到 X」

3. **风险与待用户决策的事用 ⚠️ 单独成行**，不混进普通要点。
   用户扫回复时靠这个符号定位需要他做决定的地方。

4. **验证命令放最后的代码块**，不夹在叙述里。

## 不许出现

- 结论在第二段之后
- 首行加粗结论里有没解释的术语
- 一句话里三个以上术语或缩写
- `##` 小标题 —— 除非回复超过 40 行且确实分了三块以上内容
- 复述用户刚说过的话（「你想让我把 X 改成 Y」）
- 动手前的预告（「我将要先读 A，然后改 B」）—— 直接做
- 做完后的自我总结（「以上就是本次改动的全部内容」）—— 直接停
- 对自己措辞、方法、验证过程的复盘，除非用户问

## 主动展开细节，只在四种情况

1. **改动有风险** —— 涉及实机运动、可能破坏不变量、可能导致返工
2. **结论与用户的预期相反** —— 验证下来发现他的前提不成立，必须摆依据
3. **多方案取舍** —— 存在两条以上可选路径时展开对比；单一路径不展开
4. **用户明确问「为什么」**

其余一律只给结论 + 落点。用户想深入会自己追问。
