# spec —— L2 确认卡

用户很清楚自己不擅长把模糊念头说清楚，也知道自己的话里常掺着未经验证的归因。
这个 skill 的作用不是"多问几句"，是把**验证前提**和**约定验收线**这两件事强制发生在动手之前。

核心设计：**不要让用户描述，要让用户纠错。** 人对着一份写错了的具体东西挑毛病，
比凭空描述容易一个数量级。所以确认卡必须写满、写具体、敢写错，绝不能拿一串开放问题去交差。

## 第一步：出卡前先自己查（这步跳过，整张卡就废了）

约定第 7 条：凡是读代码、读日志、跑只读命令能确定的，自己确定，不许拿来问用户。
出卡前至少做完：

- 用户提到的文件 / 参数 / 节点，实际读一遍，确认现在的值和位置
- 用户描述的现象，能从日志或 `ros2 topic echo` 只读验证的，先验
- sim / hw 两侧同名文件都看一眼，判断这次到底动哪份（判断不了才升级成问题）
- 相关包 `docs/README.md` 的「不变量」表看一遍，确认方案不违反

**不许出现在确认卡里的问题**（这些是把活推回给用户）：

| 不许问 | 该怎么做 |
| --- | --- |
| 「这个参数现在是多少？」 | 自己读文件 |
| 「你想改哪个文件？」 | 自己判断并写进【方案】，让用户否决 |
| 「要不要同步 hw？」 | 自己查 hw 侧有没有对应项，给出建议再让用户确认 |
| 「你希望怎么实现？」 | 自己出方案，用户只负责说"不对" |
| 「有什么约束吗？」 | 太开放，换成具体的：「这次要不要保持 A 不变？」 |

## 第二步：追问维度（只问真正只有用户知道的）

需要问的时候，围绕这五个维度，每个维度最多一句，能不问就不问：

1. **原始观测**：你实际看到的是什么（不是你的判断）。「小车贴墙走」是观测，「代价地图膨胀不够」是判断。
2. **触发边界**：什么时候开始的？之前正常吗？中间改过什么？只在特定路段/特定地图出现吗？
3. **手段是否绑定**：你要的是这个结果，还是指定必须用这个手段？（用户常把手段说成需求）
4. **失败反例**：什么情况下你会认为这次改动失败了？—— 这一条直接产出【验收】栏。
5. **相邻影响**：hw 那边同步吗？会不会碰到已经跑通、不想动的东西？

## 第三步：七栏模板

```
【目标】<一句话，用结果描述，不用手段描述>

【事实】<已验证的，逐条附出处>
  - ... （nav2_params_neupan.yaml:87 实测值 X）
  - ... （日志原文 "..."）

【假设】<用户话里带因果/归因/比较、但我没验证的，逐条标怎么验>
  - 假设：... ｜ 验法：... ｜ 建议：先验 / 直接按此做

【方案】<要改什么，文件级，带行号>
  1. path/to/file.yaml:12  A → B
  2. ...

【不做】<明确排除的相邻改动，防止范围蔓延>
  - 不动 hw 侧同名参数
  - ...

【验收】<可观测的量或现象，事后拿它对照>
  - ...

【异议】<必填。有疑虑就直说并给替代方案 Y；确实没有就写"无异议">
```

### 填写硬规则

- **【事实】只收自己验证过的。** 用户口述的一律不算事实，除非验证过。
- **【假设】不许空着凑数，也不许把用户所有话都塞进来。** 只放会影响方案对错的那几条。
- **【异议】不许写场面话。** 「方案可行，但需注意风险」等于没写。要么指出具体哪个前提站不住，要么写「无异议」。宁可写「无异议」，不要写废话。
  **只有当异议影响方案对错时，才给替代方案 Y 让用户选。** 不影响对错的风险提示，
  陈述完直接写明「我仍按你说的做」—— 不要做成选择题，用户每多选一次就多一次改口的机会。
- **【验收】不许写「变好了」「更流畅」「更稳」。** 必须能在改完之后用一条命令或一次观察判定真假。
  确实无法当场观测的（改规则、改文档、改提示词这类），允许留空，但必须写明为什么不可观测，
  并约定一个事后复盘触发点（例如「下次再出现同类返工时，回来看这条规则有没有拦住」）。
  留空且不说明理由 = 这一栏没填。

## 示例（本仓库真实场景）

用户说：「NeuPAN 过窄门老是卡住，把 collision_threshold 调小点吧」

```
【目标】让小车通过窄门时不再停下等待或反复后退，全程保持前进。

【事实】
  - sim 侧 neupan_sim.yaml:41 collision_threshold = 0.15
  - 上一轮 commit 53a8c09 改过 backoff 逻辑，会在侧向障碍时原地转向

【假设】
  - 假设：卡住的原因是 collision_threshold 太大导致误判碰撞
    ｜ 验法：卡住时 echo /neupan/status 看是碰撞判定还是 backoff 触发
    ｜ 建议：先验 —— 若实际是 backoff 在转向，调这个参数完全无效
  - 假设：「老是卡住」= 每次都卡（还是特定那道门？）｜ 只有你知道，见下方问题

【方案】（待假设验证后确定，暂按碰撞判定成立写）
  1. src/my_bot_nav/config/sim/neupan_sim.yaml:41  0.15 → 0.10

【不做】
  - 不动 hw 侧 neupan_hw.yaml（实机间隙与仿真不同，需单独测）
  - 不动 backoff 相关参数

【验收】
  - 从餐厅到卧室（穿窄门）全程 cmd_vel.linear.x 不出现连续 3s 以上的 0 值段
  - /neupan/status 全程不出现 backoff 触发

【异议】
  有异议。调小 collision_threshold 是拿安全裕度换通过率，窄门本来就是最需要裕度的场景，
  这个方向可能加剧擦碰。替代方案 Y：先确认是不是 backoff 误触发（假设 1），
  若是，改 backoff 的侧向障碍判定阈值更对症，安全裕度不动。
  需要你先回答：是每道门都卡，还是只有某一道？
```

注意这张卡的形态：方案已经写死到行号（用户可以直接否决），异议指出了方向性问题并给了 Y，
验收是两条可执行的判据，唯一推回给用户的问题是模型确实查不到的（哪道门）。

## 第四步：出卡之后

- 等用户回话。用户没回之前不得 Edit/Write（约定第 14 条）。
- **定稿后落盘**：写成 `docs/spec/<YYYY-MM-DD>-<主题>.md`（格式见该目录 README），然后**开新会话执行**。
  对话里的卡会被上下文压缩吃掉，事后无从对照【验收】栏；新会话的实现上下文也更干净。
  例外：改完当轮就能验完的，不用落盘，直接做。
- 用户改了哪一栏，就按改后的重新过一遍——尤其【异议】被驳回时，按约定继续做完整需求，不再重复劝阻。
- 【假设】里标了「先验」的，先验完再动手，把验证结果补回【事实】。
- 实现完成后，**逐条对照【验收】栏报告**，不许用「已完成」笼统带过。
  涉及实机运动的验证命令，给用户执行，不要自己跑（约定第 15 条）。
- 实现完成后回到 `docs/spec/` 里那张卡，在顶部标结果（通过 / 未通过 / 放弃）。
