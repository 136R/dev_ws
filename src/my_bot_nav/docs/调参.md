# Nav2 调参（当前技术栈）

> 只讲**当前在用的**：ThetaStarPlanner + (RPP | NeuPAN) + costmap。
> MPPI / DWB / SmacPlanner2D **都已不在技术栈内**（相关参数与旧调参文档已删除，需要时去 git 历史找）。
>
> NeuPAN 自己的参数（两层）见 [neupan.md](neupan.md)。
>
> 下面的值取自 `config/sim/nav2_params_{rpp,neupan}.yaml`（两者的 costmap 段一致）。

## 调参顺序

**footprint → inflation → obstacle range → goal/progress checker → 控制器**。
顺序不能乱：footprint 错了，后面全白调。

---

## 1. 机器人轮廓（影响最大）

Nav2 官方：非圆形机器人**强烈建议用 `footprint` 而不是 `robot_radius`**。

当前配置：

```yaml
# local_costmap —— 多边形
footprint: "[[0.05, 0.121], [0.05, -0.121], [-0.104, -0.121], [-0.104, 0.121]]"

# global_costmap —— 圆
robot_radius: 0.1
```

> ⚠️ **两者不一致，值得留意。** 那个 footprint 的外接圆半径是
> `√(0.104² + 0.121²) ≈ 0.159 m`，比 global 的 `robot_radius: 0.1` **大不少** ——
> 意味着全局规划器眼里的车比局部 costmap 认为的小，可能规划出局部走不通的路径。
>
> 如果出现"全局规划有路、局部却卡住不动"，先查这里。
> （当前这么配是刻意让全局能穿更窄的缝，还是遗留问题，未确认。）

## 2. 膨胀层

| 参数 | local | global | 含义 |
| --- | --- | --- | --- |
| `inflation_radius` | `0.17` | `0.20` | 膨胀半径(m)。机器人中心到障碍的最小期望距离 ≈ 此值 |
| `cost_scaling_factor` | `6.0` | `6.0` | 代价衰减速率，越大衰减越快（Nav2 默认 10.0） |

**规则：global 的 `inflation_radius` 必须 ≥ local 的。** 否则全局路径可能穿过局部 costmap
里的高代价区，导致控制器频繁偏离。当前 `0.20 ≥ 0.17` ✓

代价公式：

```
cost = 253 × e^(−cost_scaling_factor × (距离 − inscribed_radius))
```

`cost_scaling_factor` 越小 → 膨胀区代价越平缓 → 机器人敢靠近障碍。

> RPP 的 `inflation_cost_scaling_factor: 6.0` **必须等于** local costmap 的
> `cost_scaling_factor` —— 它靠这个反推距离来做速度调节。不一致会导致减速时机错乱。

## 3. 障碍物层距离

| 参数 | local | global | 含义 |
| --- | --- | --- | --- |
| `raytrace_max_range` | `3.0` | `4.0` | 用射线**清除**障碍的最远距离(m) |
| `obstacle_max_range` | `2.5` | `3.5` | **标记**障碍的最远距离(m) |

**规则：`obstacle_max_range` 必须 < `raytrace_max_range`。** 否则标记了却清不掉，
costmap 里会留下"幽灵障碍"。当前两处差值均为 0.5m ✓

## 4. 目标到达判断

```yaml
general_goal_checker:
  xy_goal_tolerance: 0.05     # 5cm，比 Nav2 默认(0.25)严格 5 倍
  yaw_goal_tolerance: 6.28    # = 2π，等于不约束朝向
```

`xy_goal_tolerance: 0.05` 要求控制器和 SLAM 定位误差都 < 5cm。
**如果车在目标点附近反复来回**，说明定位或控制误差超了 5cm，放宽到 `0.1` 即可。

`yaw_goal_tolerance: 6.28` = 不限制终点朝向 —— 对差速车的点到点导航是正确的
（NeuPAN 的 `line` 跟踪也本来就不保证终点朝向）。

## 5. Progress Checker（防卡死）

```yaml
progress_checker:
  required_movement_radius: 0.3    # 10 秒内至少移动 0.3m
  movement_time_allowance: 10.0
```

超时未达标 → 判定卡死 → 触发 recovery（spin / backup）。

车速 0.3 m/s 时 10 秒理论能走 3m，要求 0.3m 是宽松的。但**窄空间里缓慢挪动可能误触发** ——
放宽成 `0.1` / `15.0` 即可。

> 开了 NeuPAN 的 backoff 后，后退超过 `max_cycles` 会主动硬停，**正是为了把控制权交还给
> progress checker**（让它去 spin / replan）。两者是配合关系。

## 6. 频率

| 参数 | 值 | 说明 |
| --- | --- | --- |
| `controller_frequency` | `20.0` | 控制器（RPP / NeuPAN）执行频率 |
| `expected_planner_frequency` | `1.0` | 全局重规划频率 |
| `bt_loop_duration` | `10` (ms) | 行为树 tick 周期 = **100Hz** |

> `Behavior Tree tick rate 100.00 was exceeded` 是**无害警告** —— 只说明某次 tick 超过了 10ms，
> CPU 争抢所致（开着 app 前端 + Gazebo + neupan 推理时常见），导航照常成功。
> 行为树本来也不需要 100Hz（它只是轮询各 action server 的状态）。
> 想消掉：`bt_loop_duration: 20`（50Hz），功能上无损失。

## 7. 控制器

- **RPP**（`controller:=rpp`，默认）：`desired_linear_vel: 0.3`，
  其余按 [Nav2 官方 RPP 文档](https://docs.nav2.org/configuration/packages/configuring-regulated-pp.html)
- **NeuPAN**（`controller:=neupan`）：见 [neupan.md](neupan.md)
