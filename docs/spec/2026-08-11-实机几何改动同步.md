## 【第 6 步执行记录】2026-08-13 —— 轮径标定

### 一个测量陷阱，先记在最前面

首轮 8 组数据的比值随距离单调爬升（0.919 → 0.998），拟合成
`odom = 1.05312 × true − 0.1776 m`，R² = 0.999984、残差 RMS 3.0 mm。
当时据此判断"尺度多算 5.3% + 每趟固定少 0.178 m"两项误差叠加，并开始排查那个固定缺口。

**实际上固定缺口是量尺方式造成的系统偏差，真值须一律减 0.167 m。** 排查过程留档：

| 候选 | 怎么排除的 |
|---|---|
| EKF 速度估计滞后 | 实测同一趟 `/diff_cont/odom` 与 `/odometry/filtered` 位移**逐位相同**（1.8657 / 1.8657）；且结构上不可能 —— `position_feedback` 默认 `true`（`diff_drive_controller_parameters.hpp:88`，两份 yaml 都没改），odometry 走累积角度差分而非速度积分，加减速快慢不影响位移总量 |
| 固件/编码器丢帧 | 丢帧是随机过程，不可能 9 次恰好丢同样多。**固定偏置稳定到 ±3 mm 是几何量的特征，不是通信或动力学的特征** |
| 打滑 | 同上；且 0.178 m 的滑行距离在 0.3 m/s 下不合理 |

> **教训（与 F12 同源）**：`odom = a·true + b` 里 `b` 显著非零时，先怀疑量尺基准，不要先怀疑系统。
> 一个提前能发现的破绽：真值 0 时里程计必然是 0，但该模型给 −0.178 —— **拟合直线外推不到原点，
> 说明"每趟固定丢一段"根本不是一个能成立的物理过程**，它只是区间内的假象。
> 当时被 R²=0.999984 说服了，没做这个 sanity check。

### 标定数据（真值 = 尺读数 − 0.167）

10 组，0.557 ~ 2.983 m，速度 0.3 m/s，读 `/diff_cont/odom` 的 X：

| 真值 | 0.557 | 1.148 | 1.313 | 1.333 | 1.481 | 1.773 | 2.381 | 2.523 | 2.858 | 2.983 |
|---|---|---|---|---|---|---|---|---|---|---|
| odom | 0.5849 | 1.2085 | 1.3800 | 1.4060 | 1.5560 | 1.8657 | 2.5000 | 2.6540 | 3.0100 | 3.1430 |
| 比值 | 1.0501 | 1.0527 | 1.0510 | 1.0548 | 1.0506 | 1.0523 | 1.0500 | 1.0519 | 1.0532 | 1.0536 |

```

仿射对照    截距 b = −1.7 mm            （修正前是 −177.6 mm，已塌成 0）

### 回填结果

标定前 `left 0.9975 / right 1.0`（0.9975 是用户为消除固定左偏而设，**该比值是跑直用的，
不能单独动**）。两个同除 1.05235，保持左右比不变：

|---|---|---|

### 独立复验（V7）

用回填后的配置另跑一趟，**不复用标定集**：真值 **1.185** / `/diff_cont/odom` **1.1847**

**交叉验证（强）**：该值与底盘重做前旧标定的有效半径平均值 **0.0332341** 差 **0.05%**。
两代轮子各自独立标出同一个数 → **H3「旧 multiplier 随几何变更失效」在轮径这一项上不成立**，
旧值补的根本不是几何，是轮胎压陷。（打个折：轮子确实换过，几何卡第 0 步实测厚度 0.027→0.028，
所以这个吻合有巧合成分；但它独立佐证了 0.9479/0.9503 这个量级没算错。）

点动对齐准不准"的误差一并消掉；IMU 自身 0.118% 的标度误差相对 4.8% 的修正量可忽略。

```

k₂ = 3426.94/3600.18 = 0.95188
k  = 0.95209                      （用名义 3600° 算得 0.95180，差 0.03%，不改变结论）
新 wheel_separation_multiplier = 1.0 × k = 0.95209
有效轮距 = 0.192 × 0.95209 = 0.18280 m

### 两个要留意的点

**一、有效轮距比卡尺量的胎面中心距小 9.2 mm（−4.8%）。**
标定工况是原地转，属纯 scrub（轮胎侧向刮擦），与行进中大半径转弯的滑移模式不同。
**该值对后者未必最优** —— 若导航转弯系统性偏大/偏小，第一个该回来看的就是这条。
已就地写入 yaml 注释。

**二、与旧标定的修正量差得多。** 旧几何 `0.175 × 0.98012 = 0.17152`（修正 −2.0%），
新几何 `0.192 × 0.95209 = 0.18280`（修正 **−4.8%**）。轮径那一项两代吻合到 0.05%，
轮距这一项却差了一倍多。可能来自轮子换过（厚度 0.027→0.028）或旧标定工况不同，
**未查证，记此备考**。

（台架基线 4.27°/3600°，判定线比基线松一倍）→ **它会以"通过"的形式给出假阳性**，
而轮距一次都没被验到。

**但轮距不能因此不标** —— `wheel_separation` 在 `diff_drive_controller` 里是双向的
（humble 分支 `diff_drive_controller/src/diff_drive_controller.cpp`，本机只装了二进制，无源码副本）：

```cpp
:143  const double wheel_separation = params_.wheel_separation_multiplier * params_.wheel_separation;
:257  const double velocity_left  = (linear_command - angular_command * wheel_separation / 2.0) / left_wheel_radius;
:259  const double velocity_right = (linear_command + angular_command * wheel_separation / 2.0) / right_wheel_radius;
:302  odometry_.setWheelParams(wheel_separation, left_wheel_radius, right_wheel_radius);
```

同一个值，:302 走正解（odom yaw，**EKF 不用**），:257-260 走逆解（`cmd_vel` → 左右轮速命令，
**在控制通路上，跑不掉**）。两个可用于标定的比值：

```
① 实际角速度 / 指令角速度      = (L_cfg / L_true) × (r_true / r_cfg)
② odom_yaw   / 真实yaw         = (r_cfg / r_true) × (L_true / L_cfg)
```

②的 `v_R/v_L` 来自编码器实测，真值由人工数圈给出，故②可标 —— 这就是第 6 步第 2 条的依据。

**轮距错了的后果**（说明为什么不能省）：闭环部分会被掩盖 —— RPP/NeuPAN 从 EKF（即 IMU）
看到真实角速度，会反馈修正，不会"转不到位"；但 **NeuPAN 是 MPC，它按"发 ω 就得到 ω"
预测未来轨迹，增益失配是实打实的**，表现为转弯段抖动或超调。键盘遥控是纯开环，手感直接不对。

> ⚠️ **V7 用 `/odometry/filtered` 是对的，不要"顺手统一"成 `/diff_cont/odom`。**
> filtered 的 x 位移来自 `odom0` 的 vx 积分（vx 是 EKF 唯一采信的轮速量），而卷尺是外部真值
> —— 这一对确实能测出 `r_cfg/r_true`。**只有 yaw 那条通道是断的，位移通道是通的。**

### 第 4 步 — NeuPAN yaml（对齐数字，不重训）

**实现时必须先查一件事**：NeuPAN 的 `length/width` 矩形是以哪个点为中心的。
若它默认以 `base_link` 居中，F9 那 47 mm 偏置会让它把车算错位置（前方多算 47 mm、
后方少算 47 mm）。查 `src/neupan_cpp/libneupan/` 里 `length/width` 的消费点，
确认后再决定是否需要额外偏置补偿。查不出来就在卡里记下并升级为新的假设，不要猜。

> **F10（2026-08-12 执行时查证，结论：确实以 `base_link` 居中）**
> 消费点是 `src/neupan_cpp/libneupan/src/robot.cpp:84-96` 的 `Robot::diffRectangle()`：
> ```cpp
> const double sx = -(length - wheelbase) / 2.0;   // :87
> const double sy = -width / 2.0;                  // :88
> ```
> 四个顶点由 `(sx, sy)` 起算，`wheelbase` 来自 `neupan_planner.cpp:65`
> `c.wheelbase = r["wheelbase"].as<double>(0.0)`。**两份 neupan yaml 都没有 `wheelbase` 键
> → 取默认 0.0 → `sx = -length/2`，矩形在 x、y 两个方向都以 `base_link` 居中。**
> 因此 F9 那 47 mm 后偏 **无法**被当前配置表达：NeuPAN 认为车体 x 范围是
> `[-0.11, +0.11]`，实际是 `[-0.157, +0.063]` —— **后方少算 47 mm**（危险方向），
> 前方多算 47 mm（保守方向）。
>

### 第 6 步 — 重标定（几何改完后必做）

按约定第 15 条，涉及实机运动的命令由我给出、用户执行：

**两条标定有先后依赖，不能换序**：轮距的判据里含轮径比（见 F13 的 ②），
轮径没标准就去标轮距，会把轮径误差吸进 `wheel_separation_multiplier`。

1. **轮径标定** — 直线跑 2 m，卷尺量实际位移，与 `/odometry/filtered` 的位移比
   → `left/right_wheel_radius_multiplier`。
   与轮距解耦：直线段 `angular_command = 0`，F13 的两个公式里 `L` 都被消掉。

2. **轮距标定** — 原地转 **10 圈**，**人工数圈得真值 3600°**，读 **`/diff_cont/odom`** 的累计 yaw
   （**不是 `/odometry/filtered`** —— 后者的 yaw 里没有任何轮速成分，见 F13）：

   ```
   k = odom_yaw / 3600°            # 由 F13 ②，轮径已标准时 k = L_true / L_cfg
   新 wheel_separation_multiplier = 旧值 × k
   ```

   这条只依赖编码器 + 人工数圈，**不依赖 IMU 精度，也不依赖电机能否精确跟踪指令角速度**。

   > 替代法（省掉数圈，精度略低，非首选）：发固定 ω 转 T 秒，读 `/odometry/filtered`
   > 的累计 yaw Δψ，`k' = Δψ / (ω·T)`，新 multiplier = 旧值 **÷** k'。
   > 代价是把 IMU 标度误差（台架实测 0.118%，见 IMU 卡）和电机跟踪误差一并引进判据。

3. **雷达 yaw 外参** — 正对平直墙，由 `/scan_filtered` 拟合墙面法向修正 C2，
   回填 `robot_bringup.launch.py:40`
4. **IMU 复核** — C5 朝向未变，但 C4 位置变了（y 从 0 挪到 +0.04，离地 0.0599→0.084）。
   角速度不受安装点位置影响（刚体各点角速度相同），EKF 又只吃 yaw，所以预期影响很小；
   但仍要按 `my_bot_hw/docs/imu标定.md` 跑一次零偏复核，确认换装过程没碰坏轴向。
