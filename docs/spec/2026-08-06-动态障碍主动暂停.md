# 动态障碍主动暂停 —— 看见有人挡路就停下等，而不是卡住后才等

> 来源：`~/.claude/plans/10-30-m-shimmering-treehouse.md` 的 B 段（2026-08-06 批准）。
> 前两卡：`2026-08-06-电量感知-固件与协议.md`、`2026-08-06-低电归位-任务层.md`。
> **排期上先做完 A 再做 B，不并行**（B 触碰 BT 和看门狗，是全系统最贵的地方）。

## 【目标】

把"遇到动态障碍就等"的触发时机，从**卡住之后**（BT 恢复链里的 `Wait`）
提前到**看见就停**，减少怼上去再退的观感和碰撞风险。

**明确不追求**"提高通过率" —— 见【异议】1。

## 【事实】

### A 组 —— 本会话亲自验证

1. **系统已经在做"暂停等待"了**，且这个策略判断上一轮已经做过并落地：
   `src/my_bot_nav/config/common/bt/navigate_to_pose_custom.xml:78-86` 的恢复链
   `RoundRobin` 里有 `<Wait wait_duration="5"/>`，注释原文：
   > `Wait —— 唯一真正有效的。障碍是别人在动，等它走开。`
   > `wait_duration 2→5：实测(2026-07-22)动态障碍从压住目标到走开约需 10s，2s 太短。`

   → **本卡的增量只是触发时机**，不是引入新策略。

2. **BT 恢复链有跨包预算约束**（同文件 10-20 行注释）：
   `number_of_retries` 上限 N=4，受 `nav_watchdog` 的 `stuck_timeout_sec=30` 制约；
   当前值 N=2，实测一轮恢复 ≈2.2 s、Spin 1.8 s、Wait 5 s。

3. **`progress_checker` 会打死"零速方案"**（`nav2_params_hw_neupan.yaml:96-97`）：
   `required_movement_radius: 0.1`、`movement_time_allowance: 8.0`。
   `bt_loop_duration: 10`（ms，同文件 :17）。

4. **local_costmap 反应太慢，不适合做差分源**（同文件 :135）：`publish_frequency: 1.0`（1 Hz）。
   且它是 `voxel_layer + keepout_filter + inflation_layer` 的**合成结果**
   （膨胀会把 cost 糊开，分不清障碍本体；keepout 区会被误判成非静态）。
   global_costmap 同样 `publish_frequency: 1.0`（:186）。

5. **车半宽 = 0.126 m** —— footprint
   `[[0.05, 0.126], [0.05, -0.126], [-0.104, -0.126], [-0.104, 0.126]]`（:145）。
   → `corridor_half_width = 0.25` 的取值依据（0.126 + 余量）。

6. **costmap 分辨率 0.05 m**（:142 / :194）→ `static_dilate_cells = 3` 即 0.15 m。

7. **`plugin_lib_names` 在 `nav2_params_hw_neupan.yaml:24`**（bt_navigator 段内）。

8. **⚠️ `/map` 会被 slam_toolbox 持续回填**（`mapper_params_hw.yaml:29,40,42`）：
   `mode: localization` + `map_update_interval: 1.0` + `resolution: 0.05`。
   → 站着不动的人**可能被写进发布的地图**，这是本卡最隐蔽的失效模式（见【方案】缓解）。

9. **现成的仿真场景**（`src/my_bot/worlds/`）：
   `dynamic_indoor_crossing.sdf`（2 个演员）、`home_4rooms_dynamic.sdf`（6 个演员，
   对应"6~10 人办公室"密度）、`test_dynamic.sdf`（1 个）、
   **`dynamic_indoor_crossing_static.sdf`（同场景无演员版）**
   → **误报率测试直接用这个对照场景**，不用自己搭。

10. **`nav_watchdog.py` 的参数只有部分热读**：`stuck_timeout_sec`(74行)、`min_progress_m`(77行)
    是 property 每次 `_check` 重读；`check_period_sec`(48行) 在 `__init__` 读一次，
    **改它要重启节点**。`ACTIVE_STATES = ('NAVIGATING', 'RETURNING')`（:33）。

11. **NeuPAN backoff 现状**（`config/hw/neupan_hw.yaml:48-52`）：
    `enabled: true`、`release_distance: 0.15`、`max_cycles: 80`、`turn_speed: 1.2`
    （侧向障碍原地转开）。

12. **历史教训（必须避开）**：曾实现过断点聚类 + 贪心最近邻的动态障碍 tracker +
    预测 costmap layer，因 track ID 爆炸、速度估计尖峰导致预测点飞到隔壁房间而**完全回退**。
    → 本卡方案**无 ID、无数据关联、无速度估计、无预测、不新增 costmap layer**。

### B 组 —— 子 agent 核查、已给出处，**实现第一步先复核**

13. `ReactiveFallback` 每 tick 重评估第一个孩子，其返回 RUNNING 时会 halt 后面的孩子。
14. BT.CPP 的 `ConditionNode` **不允许返回 RUNNING** → 必须做成 `Action` 节点。
15. FollowPath 被 halt 时，`controller_server` 的 goal 被 cancel → `publishZeroVelocity()`；

## 【假设】

1. **"提前停"能显著改善观感/减少碰撞。**
   这是做这件事的全部理由，但**没有量化基线** —— 当前"怼上去再退"发生的频率是多少，
   没测过。｜ 验法：B1 阶段的检测器本身就是测量工具 ——
   先只观测不动手，统计"在真实巡逻中每小时有多少次本该提前停"。
   ｜ **建议先验**：B1 跑完若发现一小时也遇不到几次，B2/B3 的性价比要重新评估。

2. **误报率能压到 <1%。**
   靠静态膨胀 3 格 + `min_points ≥ 3` + `set_hold_sec 0.4` 三重过滤。
   ｜ 验法：B1/B1b 的误报闸门。｜ **过不了就停下来调，不许进 B2**（见【验收】）。

3. **`/map` 回填不会在 60 s 内把站立的人写进地图。**
   ｜ 验法：B1 的验收 1-5（站 60 s 前后 `/map` 做差，新增占据格必须为 0）。
   ｜ **必须验** —— 若为真，缓解措施（只缓存首帧）从"保险"变成"必需"。

4. **新建 C++ BT 插件包能顺利被 nav2 加载。**
   BT.CPP 版本、`nav2_behavior_tree` 的注册宏、`plugin_lib_names` 的加载路径都可能卡住。
   ｜ 验法：见【方案】B2 的"先跑通空插件"步骤。
   ｜ **必须先验**，这是 B 里工具链风险最高的一步。

## 【方案】

### B1 检测器（只观测，不动手）

新增 `src/my_bot_nav/scripts/dynamic_block_detector.py`（Python + numpy），10 Hz：

1. 无新鲜 `/plan`（age > `plan_stale_sec`）或 `/task/status.state` 不在
   `NAVIGATING|RETURNING` → 直接 `blocked=false`
2. `/scan_filtered` 光束端点向量化转到 **map 帧**（路径和静态地图都在 map 帧，只算一次变换）
3. **静态判定**：只有落在"已知空闲"格（`0 ≤ v < free_cost_max`）的点才算候选动态障碍。
   **占据格、未知格(−1)、越界一律当静态忽略** —— 刻意的保守失效方向
4. **定位余量**：地图加载时对占据集合做一次**二值膨胀 `static_dilate_cells=3`（0.15 m）**，
   抵消定位抖动。加载时算一次（numpy 移位或运算，2000² 图上几毫秒）
5. **走廊判定**：用 `map ← base_footprint` 找路径最近点，向前累积弧长到 `lookahead_m=2.0`，
   跳过最前 `skip_near_m=0.10`（车身内自反射）。候选点到该段折线最近距离
   ≤ `corridor_half_width=0.25` 即命中
6. `blocked_raw = (命中点数 ≥ min_points=3)`
7. **非对称迟滞**：置位需连续 `set_hold_sec=0.4`，复位需连续 `clear_hold_sec=1.2`
   —— **快置位（人走过来要立刻停）、慢复位（别一走开就冲）**

**⚠️ `/map` 缓存策略（事实 8 的缓解，必须做）**：
**只缓存 map 名变化后收到的第一帧 `/map`，之后的更新一律不接受**
（刷新触发条件复用 `~/.maps/current_map` 变化机制）。
否则站着不动的人被 slam 写进地图 → 检测器认为那是墙 → 永远不再暂停，
**且这个失效完全静默**，表现为"这功能时灵时不灵"。

**输出**：
- `/nav/obstacle_pause`（`std_msgs/Bool`, 10 Hz，故意做成最蠢的类型）
- `/nav/obstacle_pause/status`（`std_msgs/String` JSON, 1 Hz + 变更时）：
  `blocked / point_count / nearest_dist / paused_for_sec / budget_left_sec /
  reason ∈ {CLEAR, BLOCKED, TIMEOUT, COOLDOWN, DISABLED, NO_PLAN, NO_TF, NO_MAP}`
- `/nav/obstacle_pause/points`（Marker，`publish_debug=true` 时才发）
  —— **这是唯一能把误报调下去的工具，务必做**

**全部参数进 `src/my_bot_nav/config/common/obstacle_pause.yaml`，
且每帧循环开头重读参数服务器**（照抄 `nav_watchdog.py` 的热读模式，事实 10），
支持 `ros2 param set` 边跑边调、不重启 Nav2：

| 参数 | 默认 | 调大的后果 |
|---|---|---|
| `set_hold_sec` | 0.4 | 更迟钝、漏停 |
| `clear_hold_sec` | 1.2 | 人走开后等更久才起步 |
| `lookahead_m` | 2.0 | 更早停，但更易被远处静态误差误触 |
| `corridor_half_width` | 0.25 | 路边站着的人也会触发 |
| `skip_near_m` | 0.10 | — |
| `min_points` | 3 | 抗噪但漏检细物（人腿） |
| `static_dilate_cells` | 3 | 真墙更不会误判为动态，但贴墙的人也被当墙 |
| `free_cost_max` | 65 | — |
| `max_pause_sec` | 20 | 单次最长暂停 |
| `max_pause_total_per_goal_sec` | 60 | **看门狗安全带，不建议调大** |
| `cooldown_sec` | 30 | — |
| `plan_stale_sec` | 5.0 | — |
| `flag_stale_sec` | 1.0 | BT 节点侧：超时未收到视为 false |
| `enabled` | true | **总开关热改**，怀疑它捣乱时设 false 即退回原行为 |
| `publish_debug` | false | — |
| `debug_force_blocked` | false | 强制阻塞，B2 预算负测试用（**走参数，不走 `ros2 topic pub`，否则绕过预算逻辑**） |

### B2 接 BT

**先跑通空插件再写真逻辑**（假设 4 的验法）：
新建包 `src/my_bot_bt`，先做一个永远返回 `FAILURE` 的空 Action 节点，
加进 `plugin_lib_names`，确认 nav2 能加载、导航行为与改动前一致 —— **工具链通了再写真逻辑**。

**节点 `PauseOnDynamicObstacle`（Action，不是 Condition —— 事实 14）**，语义只有两条：
- flag 为 true 且不陈旧 → **RUNNING**
- 否则 → **FAILURE**
- **永远不返回 SUCCESS**

树的改法（`navigate_to_pose_custom.xml` 第 2 步）：
```xml
<ReactiveFallback name="PauseOrFollow">
  <PauseOnDynamicObstacle topic="/nav/obstacle_pause"/>
  <RecoveryNode number_of_retries="1" name="FollowPath">   <!-- 原样不动 -->
      <FollowPath path="{path}" controller_id="FollowPath"
                  goal_checker_id="general_goal_checker"/>
      <ClearEntireCostmap service_name="local_costmap/clear_entirely_local_costmap"/>
  </RecoveryNode>
</ReactiveFallback>
```

**为什么不用"零速进 twist_mux"**：NeuPAN 仍在跑、只是被 mux 吞掉，机器人不动
→ 事实 3 的 `movement_time_allowance: 8.0` 在 8 秒后判失败 → FollowPath abort
→ 烧掉 `number_of_retries=2` 预算 → 整个 NavigateToPose 可能 abort。
要撑 20 秒暂停就得把它抬到 20+，而那是**唯一能抓到"NeuPAN 顶死在墙上"的检测器** ——
等于为新功能拆掉老保护。

**(b) 的决定性优势**：FollowPath 是被**挂起**而非**饿死**，progress_checker 根本没在跑；
恢复时 FollowPath 作为**新 goal** 重发，8 秒窗口从头开始，白赚一层容错。

> ⚠️ **必须写进节点注释和单测的地雷**：若该节点返回 SUCCESS，
> `ReactiveFallback` → SUCCESS → `PipelineSequence` 最后一个孩子成功
> → **整个 NavigateToPose 报告"已到达"**，机器人明明停在半路却上报成功。

### B3 看门狗整合 —— 本卡最大的坑

**不解决就是净负收益**：暂停 20 s + 减速的几秒 → 超过 `stuck_timeout_sec=30` 内位移 <0.15 m
→ `nav_watchdog` 发 `/goal_pose/cancel` → NAVIGATING 时**丢弃该任务**。
用户体验变成"有人挡路，机器人把任务扔了" —— **比现在更糟**。

**三层解法，缺一不可**：

1. **`nav_watchdog.py` 订阅 `/nav/obstacle_pause`，把暂停时长从卡死计时里扣掉**：
   新增 `self.paused_accum`，每个 `_check()` 周期内 flag 为真就 `paused_accum += check_period`；
   判定改为 `stalled_for = now − baseline_time − paused_accum`；
   `_reset_baseline()` 里清零 `paused_accum`。

   > **绝不能改成"暂停时 `_reset_baseline()`"** —— 那会连**位置基准**一起重置，
   > 让"挪一点点→暂停→再挪一点点"的机器人**永远逃过看门狗**。
   > **只扣时间、不动位置基准**，是这里唯一正确的形状。

2. **检测器自设硬预算**：单次 `max_pause_sec=20`，
   **每目标累计 `max_pause_total_per_goal_sec=60`**（超了自我禁用直到目标改变）。
   这是第 1 条的安全带 —— 单独有第 1 条，一个疯掉的检测器就能把看门狗**永久架空**。

3. **可观测性**：`/nav_watchdog/status` JSON 里**分开**发
   `stalled_for_sec` 和 `paused_accum_sec`，事后能直接判定是哪个机制在起作用。

新增两个 `nav_watchdog` 参数：`pause_topic`（默认 `/nav/obstacle_pause`）、
`subtract_pause_time`（默认 true，**设 false 即完全退回今天的行为**，方便对比排查）。

**顺带更新两处跨包注释契约**（本项目把它们当契约）：
- `navigate_to_pose_custom.xml` 顶部的 `number_of_retries` 预算注释：补
  "暂停不消耗 BT 重试预算（FollowPath 是被 halt 不是 fail），N=2 结论不变"
- `task_params.yaml` 的 `stuck_timeout_sec` 反向耦合注释：补扣除规则与上限

### 退出条件与降级

| 项 | 值 |
|---|---|
| 正常退出 | 走廊连续空闲 `clear_hold_sec = 1.2 s` |
| 单次最长 | `max_pause_sec = 20 s`（事实 1 实测"约需 10 s"，取 2×） |
| 每目标累计 | `max_pause_total_per_goal_sec = 60 s` |
| 超时后 | 强制 `blocked=false` + `cooldown_sec=30` 内不得重新置位 |
| 立即清除 | 目标改变 / `/plan` 消失 / **TF 查询失败** / state 离开 NAVIGATING\|RETURNING |

**TF 失败必须 fail-open 成不暂停** —— 卡死的暂停比漏掉的暂停危险得多。

**超时后的回落 = 今天的行为，一字不差**：FollowPath 恢复 → NeuPAN 挤 / backoff 转开
→ progress_checker 8 s → BT 恢复链（Clear→Wait 5s→Spin→BackUp）→ nav_watchdog 30 s。
即：**本方案是一个严格叠加、时间有上限的前缀**，把检测器整个杀掉，行为退回改动前。

### 与 NeuPAN backoff 的协调：结构上不冲突，无需仲裁

暂停期间 FollowPath 被 halt，**NeuPAN 根本没在 tick**，backoff 物理上无法触发。
谁先手是**几何决定的**：暂停在 2 m 触发，backoff 要 `min_distance < 0.15 m`（事实 11）
—— 正常遭遇里 2 m 处就停了，走不到 0.15 m。
唯一真打架的场景是暂停预算耗尽而人还站在近处，此时 FollowPath 恢复、backoff 转开
—— **这正是期望的降级顺序（先等 → 再绕 → 再放弃）**。

## 【不做】

- **不改 `neupan_hw.yaml` / `neupan_sim.yaml` 的 `backoff` 段一个字**
  （调 `release_distance` = 在 MPC 里重新实现暂停，而 MPC 分不清墙和人，
  结果是窄门里也停死）。
- **不做任何目标跟踪** —— 无 ID、无数据关联、无速度估计、无预测（事实 12）。
- **不新增 costmap layer**、不碰 `voxel_layer` / `keepout_filter` / `inflation_layer`。
- **不改 `progress_checker` 的 `movement_time_allowance`**（那是抓"顶死在墙上"的唯一检测器）。
- 不改全局/局部 planner、不改 `ThetaStarPlanner` / `SmacPlanner2D` 配置。
- 不碰固件、不碰电量相关的任何东西（前两卡的范围）。
- 不改前端 Dart 代码（只在 `/task/status` 加 `obstacle_paused` 字段供将来用）。

## 【异议】

**有三条。第 1 条影响"值不值得做"，已在规划阶段提出并由你决定继续；

### 1. 本卡的收益比直觉小，且没有量化基线（已提出，你已决定做）

事实 1 显示系统**已经在做暂停等待**，只是挂在恢复链里、卡住后才等。
本卡的增量只是**提前**，主要改善观感和减少碰撞，**不改变"能不能过去"**。

更实在的问题是：当前"怼上去再退"到底多久发生一次，**没有测过**（假设 1）。
所以我把 B1 设计成"只观测不动手"，并加了验收 1-6（真实巡逻 1 小时统计置位次数）。

**建议在 B1 结束时停下来看这个数**：如果一小时也遇不到几次，

B1 本身是个可独立交付的诊断工具，停在那里不算浪费。
**你已决定做，我仍按完整计划执行**，只是把这个决策点显式标出来。

### 2. 修复看门狗的同时，给了检测器一把"关掉安全网"的钥匙

扣除暂停时长是必须的，但一个抖动的检测器（定位漂移导致 flag 高频闪烁）
能把 `paused_accum` 刷满，让看门狗形同虚设 ——
**症状恰好是"机器人卡在走廊里，谁也不管它"**，正是 watchdog 当初被造出来解决的问题。

三层解法里的第 2 层（每目标 60 s 硬预算）和第 3 层（分开发布 `paused_accum_sec`）
**不是锦上添花，是这条风险的唯一控制手段**。验收 3-3/3-4 的"杀掉 detector 后完全回退"
是最后的兜底。**我仍按此做。**

### 3. C++ BT 插件包是工具链风险最高的一步（假设 4）

确认能被 nav2 加载、导航行为不变（验收 2-0），再写真逻辑。
