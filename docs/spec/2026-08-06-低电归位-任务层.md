# 电量感知（二）—— 电压→百分比 + 低电自动归位

> 来源：`~/.claude/plans/10-30-m-shimmering-treehouse.md` 的 A3/A4/A5 段（2026-08-06 批准）。
> **前置**：`2026-08-06-电量感知-固件与协议.md` 必须先通过（本卡依赖 `/battery_raw`）。

## 【目标】

机器人在电量低时自主放弃当前任务、回到待命点停下，并拒绝新召唤，直到充电恢复。

终点：一次真实巡逻中电量自然跌破阈值 → 机器人自己回到 HOME 停住 → APP 上能看到原因。

## 【事实】

### A 组 —— 本会话亲自验证（`task_manager.py` / `nav_watchdog.py` / 前端）

## 【假设】

1. **电池是 3S 锂电（11.1 V 标称）。**
   ｜ 验法：上一卡 A1 用万用表量满充电压时已确认。
   ｜ **本卡开工时先向上一卡的结论确认**，`battery.yaml` 的整张表都建立在它上面。

2. **电压→百分比用规格表手填 5 点足够（±10%）。**
   用户 2026-08-06 明确：百分比精度 ±10% 即可，不跑整天放电实验。
   ｜ 验法：验收 3-2（GUI 显示值 vs 按表手算值差 ≤2%）验的是**代码对**，不是电池模型对。
   模型准不准要等实际用一两周后回调。｜ 不预先验。

3. **`low_voltage = 10.70 V` 对应约 20% 电量。**
   来自规格表插值，不是实测。用户指定的是"20% 触发归位"这个**意图**。
   ｜ 验法：实际用一两周，看触发时机是否偏早/偏晚，回调这个电压值。
   ｜ 不阻塞，先按此值走。

4. **用户会"不关机充电"。**
   `resume_voltage` + `resume_debounce_sec` + 棘轮那一整套只在不关机充电时才起作用；
   若习惯是关机充电，下次开机电压已高，直接进 IDLE，这套逻辑走不到。
   ｜ 验法：A5 实机时观察用户实际怎么充。｜ 见【异议】2。

## 【方案】

### A3 粗标定 + `battery_monitor.py`

**关键设计：低电判定走电压，不走百分比。**
理由是误差链 —— 若"要不要回家"由百分比决定而百分比允许 ±10%，
20% 的触发点实际会漂到 10%~30%，与 critical 地板挤在一起。
拆开后：**电压 → 决策（精确）**、**电压 → 百分比 → GUI（允许糙）**，两条路互不污染。

新增 `src/my_bot_task/scripts/battery_monitor.py`：订 `/battery_raw`，发 `/battery_status`。

**处理链**（顺序不能改）：
```
越界剔除(<5 V 或 >20 V 判坏帧)
  → 15 点中值 (@2 Hz ≈ 7.5 s，杀电机电流尖峰)
  → EMA τ≈30 s
  → 查表线性插值 → raw_pct
  → 单调棘轮：发布值可自由下降；上升需 raw_pct 持续高于当前值 ≥180 s 才允许
              （同时置 power_supply_status = CHARGING）
  → 夹到 [1, 100]，/100 填进 percentage
```
**滤波不能省**（精度放宽了但噪声没变小）：3S 平台区 80%→20% 只掉约 0.6 V，
±10% 对应电压分辨率约 0.1 V，而上一卡验收 1-3 里行驶时读数峰峰值就有 0.20 V ——
**噪声比信号大**。棘轮专治"机器人一停下来电压回弹、界面电量往上跳"。

**`percentage` 下限夹到 1%，不能发 0**（事实 9：发 0 会被前端静默忽略，显示陈旧值）。

新增 `src/my_bot_task/config/battery.yaml`：
```yaml
battery_monitor:
  ros__parameters:
    publish_rate_hz: 1.0        # 采样 2 Hz 进滤波器，发布 1 Hz 就够（GUI 显示）
    voltage_pct_table:          # 3S 锂电示例，按上一卡实测结果替换
      - [12.60, 100]            # 满充 4.20 V/cell
      - [11.85,  75]            # 平台起点
      - [11.10,  40]            # 标称 3.70 V/cell
      - [10.50,  15]            # 平台末端，开始快速跌落
      - [ 9.60,   0]            # 截止
    median_window: 15
    ema_tau_sec: 30.0
    ratchet_rise_hold_sec: 180.0
    debug_force_voltage: -1.0   # >0 时旁路真实数据，用于仿真验 A4
```
表**必须单调递减**，启动时校验，不单调直接 error 退出。

### A4 低电归位

#### ⚠️ 不新增 `LOW_BATTERY` 状态，复用 `STOPPED` + `battery_low` 字段

事实 7/8 决定的：新增状态会让前端五个 getter 全部落空、卡片内容无分支可渲染，
且 `last_error` 只在 `STOPPED` 时显示 —— 低电拒绝召唤时用户**看不到任何提示**，
表现为"点了没反应"。要修就得改 Dart 并重新 build+部署 Flutter web。

而本项目一直珍视"**app 前端一行都不用改**"这个性质（`docs/速查.md:52`）。
复用 `STOPPED` 后：前端零改动，`last_error` 直接显示"电量低（xx%），已回到待命点"。
状态区分由 JSON 里的 `battery_low` 布尔字段承担（前端暂不消费，排障用）。

`STOPPED` 现有语义是"新召唤会拉回 NAVIGATING"，而低电要拒绝 ——
**行为差异由独立的 `self.low_battery` 标志控制，与 state 字段无关**，实现上不冲突。

#### 阈值（全部 yaml 可配 + `ros2 param set` 热改）

| 参数 | 值（3S 示例，按实测替换） | 说明 |
|---|---|---|
| `low_voltage` | 10.70 V（≈20%，用户指定） | 触发归位 |
| `resume_voltage` | 11.19 V（≈45%） | 解除低电 |
| `critical_voltage` | 9.90 V（3.30 V/cell，≈5%） | 就地停，不再尝试归位 |
| `low_debounce_sec` | 30 | 低于 low 连续这么久才置位 |
| `resume_debounce_sec` | 120 | 高于 resume 连续这么久才复位（挡"停车后电压回弹"的假恢复） |
| `battery_stale_sec` | 30 | 超时无数据 → 失效开放 |
| `override_sec` | 600 | 人工覆盖时长 |

**critical 用绝对电压而非百分比**：它是"再跑就要欠压复位"的物理地板，
与电量估计准不准无关。百分比允许 ±10% 误差，地板不允许。

#### 行为表

| 触发时状态 | 行为 |
|---|---|
| `NAVIGATING` | `low_battery=True` → `queue.clear()`（丢弃的任务名写进日志和 `last_error`）→ `_cancel_active()` → 走既有 CANCELED 路径 → `_advance()` → 队列空 → `_home()` → RETURNING |
| `WAITING` | `_clear_dwell()` → `_advance()`（同上） |
| `IDLE` | 不在 home 就 `_advance()` 回家；已 `_at(home)` 直接 `_enter(STOPPED)` |
| `STOPPED` | 尝试一次归位；失败则停在 STOPPED |
| `RETURNING` | 不动作 |
| 到 HOME 后 | `_on_result` 的 `SUCCEEDED and kind=='home'` 分支：`low_battery` 为真则 `_enter(STOPPED)` 并写 `last_error`，否则照旧 `IDLE` |

#### 必须有的三道保险

1. **critical 地板**：`voltage ≤ critical_voltage` → **不再尝试归位**，就地 `_enter(STOPPED)`。
   电压塌到底还在走廊里跑，遇到的是电机堵转/欠压复位/TF 断裂，比停在原地糟得多。
2. **失效开放**：`/battery_status` 超 `battery_stale_sec` 无消息，或 `present == false`
   → **绝不触发低电**，只置 `battery_stale: true` 并 throttle warn。
   否则一次固件回滚就会把机器人永久锁在 HOME。
3. **人工覆盖**：HTTP `POST /task/force_resume` → 清 `low_battery` 锁存 `override_sec`。
   现场演示时 20% 也得能跑，否则这功能会被自己关掉。

**`_advance()` 开头加兜底**：`if self.low_battery: self.queue.clear()`，防竞态下队列复活。

**低电时新召唤 = 拒绝，不排队**（`_on_goal` 开头拦截）：
写 `last_error = '电量低（xx%），已拒绝召唤「name」'` 并立即 `_publish_status()`。
排队意味着"充满电后几小时突然自己跑起来"，对真实使用是惊吓不是便利。

#### `/task/status` 新增字段

`battery_pct`(int) / `battery_v`(float) / `battery_low`(bool) /
`battery_critical`(bool) / `battery_stale`(bool) / `battery_override_remaining`(float)。
`state` 取值**不变**（仍是原五个）。

## 【异议】

**有两条，都不影响方案对错，仍按此做。**

### 1. 复用 `STOPPED` 是为了前端零改动，代价是状态语义被压缩

`STOPPED` 现在承载两种含义："重试耗尽/被取消"和"低电停机"，靠 `battery_low` 字段区分。
纯从建模角度，独立的 `LOW_BATTERY` 更干净。

但事实 7/8 显示，新增状态会让前端卡片内容无分支可渲染、且 `last_error` 不显示 ——
必须连带改 Dart 并重新 build+部署 Flutter web，而这与本项目一直保持的
"app 前端一行都不用改"直接冲突。**我仍按复用 STOPPED 执行。**
将来若确实需要专门的低电 UI（比如显示电池图标和充电提示），单独开一轮做前端。

### 2. `resume` 那一整套逻辑可能长期走不到（假设 4）

`resume_voltage` + `resume_debounce_sec=120` + 棘轮 180 s 只在**不关机充电**时才生效。
如果实际习惯是"关机插电、充满开机"，那下次上电时电压已经很高，直接进 IDLE，
这套逻辑一次都不会执行 —— 等于白做的复杂度。

但保留它的成本很低（约 20 行），且"边充边待命"确实可能发生（尤其待命点就在插座旁）。
**我仍按此做**，并在 A5 实机时观察你实际怎么充电；
若确认是关机充电，下一轮可以把 resume 逻辑简化掉。

方案本身无异议 —— 复用已验证的 cancel 路径、不新写状态机、三道保险（critical 地板 /
失效开放 / 人工覆盖）都已就位，且验收 4-9 明确要求"电量充足时行为与改动前完全一致"。

## 确认卡自身的两处矛盾（已复核，实现按参数表走）

### 1. 4-6 写「15 s 后 battery_stale:true」，参数表写 `battery_stale_sec: 30`

按参数表实现，实测 36 s 翻转（30 s + 1 Hz 检查粒度）。

**无实际影响**：失效开放的方向本身是安全的（只会"不触发低电"）。30 与 15 的差别仅在于
发布者挂掉后这段时间内仍用陈旧电压判定，而这个错误的方向是"可能多归位一次"，
不是"该归位却不归位"。**判据数字应改成 30**，否则以后按 15 复验会把正常系统判成失败。

### 2. 4-1 的「`low_debounce_sec + 2 s` 内触发」没有把 EMA 滞后算进去

同一张卡指定 τ=30 s。从 12.6 V **阶跃**注入 10.5 V 时，滤波电压要约 70 s 才跌破 10.70 V，
再加 30 s 去抖 ≈ 100 s，不可能落在 32 s 内。

**对功能无实际影响**，理由是阶跃不是真实工况：真实放电是慢斜坡，而 EMA 对斜坡输入的
稳态滞后就等于 τ 本身（30 s），不是 70 s 的阶跃建立时间。3S 平台区 80%→20% 约 0.6 V，
若整个放电按小时计，**60 s 滞后对应的电压误差在 0.01 V 量级**，相对 0.5 V 量级的阈值
可以忽略。

**真正值得记住的是两件事**：

- **复验 4-1 时不要用阶跃注入配 32 s 秒表** —— 会把一个工作正常的系统判成坏的。
  要么从"滤波电压穿越阈值"起算，要么像本轮那样临时缩短去抖。
- **critical 地板也走同一条 EMA**，所以电压快速崩塌时它同样晚约 30 s 触发。
  余量分两档看：9.90 V = 3.30 V/cell，距硬截止（3.0 V/cell = 9.0 V）有 0.9 V，
  但距**厂商自己标的低压线**（`docs/vendor/Inc/APP/Config.h:43` 的 `BATTERY_LOW_VOLTAGE 9.6f`）
  只有 **0.3 V**。按拐点附近 0.1~0.3 V/min 的崩塌速率估，30 s 滞后吃掉 0.05~0.15 V ——
  占 0.3 V 余量的一半。仍在安全侧，但没有我最初说的那么宽松。

  **即便如此也不建议**给 critical 单开一条"只过中值不过 EMA"的快速通道：因为在
  9.90 V 附近，**电压读数本身的不确定度比这 30 s 滞后大得多** —— 前置卡的 1-1 降级
  让标定只覆盖 12.30~12.63 V，9.9 V 是外推出来的（见 `task_params.yaml` 的阈值注释）。
  先解决"读数准不准"，再谈"读数快不快"，否则是在给一个偏置未知的量做低延迟优化。
  ⇒ **正确的下一步是补一次可调电源三点扫描，不是改滤波器。**

## 环境备忘

- **非交互 shell 不读 `~/.bashrc`，开发机（WSL）上也一样**。不设
  `RMW_IMPLEMENTATION=rmw_cyclonedds_cpp` / `ROS_DOMAIN_ID=42` / `CYCLONEDDS_URI`
  就完全发现不到节点，症状是 `ros2 topic list` 直接挂住、订阅者收不到任何消息。
  本轮的复刻脚本见验收时用的 `rosenv.sh`（内容即 `~/.bashrc` 第 129~150 行）。
- **`kill` 掉 `ros2 run` 的 pid 不会杀死它 fork 出的 python 子进程**，
  结果是同一个话题上悄悄多出好几个发布者、读数互相打架（本轮 3-2 因此错了一次）。
  验收脚本里应直接跑 `install/<pkg>/lib/<pkg>/<node>.py`，别经 `ros2 run` 包一层。
