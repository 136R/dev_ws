# 协作约定重写 + 需求甄别协议

## 【目标】

让 Claude Code 在实现前主动甄别需求本身是否成立，减少「沿着一个错误前提把文件改对了」
导致的返工 —— 而不是只在 Plan 模式里机械地沿既定需求往下走。

## 【事实】

- `CLAUDE.md:25` 以 `@docs/与我协作的约定.md` 导入该文件，每次会话随 CLAUDE.md 进入上下文
- 改动前该文件 8 条；改动后 16 条（83 行）
- **改动后常驻上下文 = CLAUDE.md 111 行 + 约定 83 行 = 194 行**，官方建议上限约 200 行
- `.gitignore:23` 为 `.claude/`，故 skill 不进版本库；`.claude/settings.json` 是先于该规则被跟踪才存活
- 改动前 `docs/与我协作的约定.md` 本身处于未跟踪状态（`git status` 显示 `??`），从未提交过
- 官方文档明确：CLAUDE.md 是 advisory（建议性），hooks 才是 deterministic（确定性）；
  过长的 CLAUDE.md 会导致 Claude 忽略掉其中一半规则
- 官方推荐的需求澄清做法：用 `AskUserQuestion` 采访用户 → 写成 SPEC.md → **开新会话执行**

## 【假设】

- 假设：Plan 模式无法甄别需求合理性，只会沿既定需求执行
  ｜ 验法：无直接验法，属该模式设计如此（它解决的是"改之前先看清代码"，不是"这个需求该不该做"）
  ｜ 处置：接受，已按此设计

- 假设：加上这套分级 + 确认卡后，返工会减少
  ｜ 验法：见【验收】，只能事后复盘
  ｜ 处置：本次改动的核心赌注，未验证

- 假设：规则从 8 条涨到 16 条不会拉低整体遵守度
  ｜ 验法：与上面【事实】里官方那条警告直接冲突，本次未验证
  ｜ 处置：**这是本次最大风险点**，复盘时的第一个怀疑对象

## 【方案】

| 文件 | 动作 |
| --- | --- |
| `docs/与我协作的约定.md` | 覆盖重写，8 条 → 16 条，分四节（定级 / 确认卡 / 表达缺陷 / 硬约束） |
| `.claude/skills/spec/SKILL.md` | 新建。四步流程 + 七栏模板 + 「不许问的问题」对照表 + NeuPAN 窄门示例 |
| `docs/spec/README.md` | 新建。确认卡归档的命名规则与生命周期 |
| `docs/spec/2026-08-04-协作约定重写.md` | 本文件 |

关键设计（三条，按重要性）：

1. **事实与假设分离** —— 用户话里带因果、归因、比较的一律进【假设】，只有验证过的进【事实】，
   只有【事实】能当方案依据。这是拦住"错误前提"的主闸门。
2. **让用户纠错，不让用户描述** —— 确认卡必须写满写具体到行号，允许写错；
   人对着一份写错的东西挑毛病，比凭空描述容易一个数量级。
3. **验收前置** —— 动手前就写死"怎么算成功"，事后拿它对照，杜绝"感觉不太对"式的争议。

## 【不做】

  按官方说法本应做成 PreToolUse hook 才有强制力，目前仍是建议性文字

## 【验收】

**不可观测，按第 6 条出口处理。** 原因：规则类改动无法在改完当场判定真假，
它的效果只在下一次真实请求到来时才显现。

约定两个复盘触发点：

1. **下次用户说出「优化一下 / 效果不好 / 好像有问题」这类模糊表述时** ——
   观察是否停下来出确认卡，而不是直接改文件。这是第 1 条 L2 触发规则是否生效的唯一判据。
2. **累计走过 3 次 L2 之后** —— 检查 `docs/spec/` 里的卡是否都标了结果。
   没标 = 第 8 条的生命周期规则形同虚设，该考虑简化而不是加码。

## 【异议】

有异议两条。两条都**不影响本次方案对错**（规则内容是用户逐条看过、改过第 12 条后确认的），
按第 5 条不做成选择题 —— **我仍按用户说的做**，记在这里供复盘时优先怀疑。

1. **规则总量与官方警告直接冲突。** 常驻上下文已到 194 行，贴着官方约 200 行的建议上限，
   而官方点名的失败模式正是「文件太长导致重要规则淹没在噪音里，Claude 忽略掉一半」。
   本次改动为了防返工而加规则，有可能反过来降低所有规则（包括原来那 8 条）的遵守度。
   若复盘时发现规则没生效，先怀疑这个，而不是继续加规则。

2. **第 8 条的落盘 + 开新会话增加了每次 L2 的仪式成本。** 真实风险不是它没用，
   是用户嫌麻烦而绕过整个协议 —— 一个被绕过的协议比没有协议更糟，因为它会造成"已经有防线"的错觉。
