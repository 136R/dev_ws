# NeuPAN 接入 Nav2 后速度偏低 —— 全局路径弧长重采样

## 【目标】

让 NeuPAN 作为 Nav2 controller 插件运行时的实际速度，恢复到与单测链路一致的水平
（受 `max_speed` 而非路径点密度约束）。

现象：同一条直线，单测链路 0.27~0.30 m/s，接入 Nav2 后只有 0.20~0.23 m/s。

## 【事实】（均已验证，附出处）

1. NeuPAN 的参考点推进是**按 curve 索引 +1**，不是按弧长
   —— `libneupan/src/initial_path.cpp:250-253`：`ref_index += inc`，
   其中 `inc = (int)(ref_speed*dt / interval_) = 1`。

2. `interval_ = dt_ * ref_speed_`（`initial_path.cpp:33`），且**在 InitialPath 构造时固定，
   不随 `setSpeedLimit()` 变化**。
   sim = 0.25 × 0.35 = **0.0875 m**；hw = 0.25 × 0.3 = **0.075 m**（`config/hw/neupan_hw.yaml:12-13`）。

3. `generateLineCurve` 在段长 < `interval_` 时**整个 while 循环不进入**，
   原样继承输入点距（`initial_path.cpp:56-62`）。

4. `pathMsgToPoints` **零抽稀**，逐个 pose 原样透传
   （`neupan_cpp_ros/include/neupan_cpp_ros/ros_conversions.hpp:57-77`）。
   单测链路则有 Douglas-Peucker（`astar_global_node.cpp:189`，`simplify_tolerance=0.05`）
   —— **两条链路的唯一差异就在这里**。

5. **实测坐实**：`ros2 topic echo /neupan_initial_path --once --field poses` 输出中，
   x 每步精确 +0.050000，y 恒定不变。0.05 / step_time 0.25 = 0.20 m/s，
   与实测速度下限 0.20 完全吻合。

6. **hw 侧同样受影响**：`ThetaStarPlanner::linearInterpolation` 按 costmap 分辨率插值，
   头文件原文 *"dist_bw_points ... has been set as the costmap resolution"*、
   *"waypoints at a distance of the value of interpolation_resolution of each other"*
   （`/opt/ros/humble/include/nav2_theta_star_planner/theta_star_planner.hpp:85-86`）；
   hw global_costmap `resolution: 0.05`（`nav2_params_hw_neupan.yaml:194`）。
   即 hw 参考速度同样被压到 0.05/0.25 = **0.20 m/s，而 `ref_speed` 期望 0.3 —— 慢了 33%**。
   sim 的另一份 `nav2_params_neupan.yaml` 也是 ThetaStar，同理。

7. `planner_->config()` 暴露 `step_time` / `ref_speed`，controller 里已在读
   （`neupan_controller.cpp:92`）→ **重采样步长可推导，无需新增配置项**。

## 【假设】

- 假设：`p_u` / `q_s` 权重不需要跟着调。
  ｜ 验法：改完看实测速度是否落回 0.27~0.30；若只升到 0.25 左右说明 `q_s` 仍在压制。
  ｜ **建议：不预先动，改完看验收 2 的结果再说。**

- 假设：重采样后 `include_initial_path_direction_: false` 从相邻点推的 theta 不会变差。
  ｜ 验法：验收 3（不出现切角）间接覆盖。｜ 建议：直接做。

## 【方案】

仅动 `neupan_cpp_ros` 一个包，两个文件：

1. **`include/neupan_cpp_ros/neupan_controller.hpp:72`** —— 在 `planFingerprint` 声明旁新增：
   ```cpp
   static nav_msgs::msg::Path resampleByArcLength(const nav_msgs::msg::Path& path, double spacing);
   ```

2. **`src/neupan_controller.cpp:200` 后** —— 新增实现（~55 行）：把路径总弧长
   **均分成 `N = ceil(total/spacing)` 段等长**，沿原路径线性插值取 N+1 个点（首尾精确保留）。

   > **实现期修正（原方案此处是错的）**：卡里原写「沿路径每 `spacing` 取一点，
   > 末段短于 `spacing/2` 时并入前一段」。离线验证证伪 —— 5.0 m 路径按 0.0874125 走完
   > 57 步后残料 0.0175 m，合并进前一段后末段变成 **0.1049 m > interval_ 0.0875**，
   > `generateLineCurve` 照样插一刀，留下 0.0174 m 残段（参考速度掉到 0.07 m/s）。
   > 「合并末段」这个策略本身不成立：合并后必然超过 `spacing`。
   > 改成 `ceil` 等分后每段恒 ≤ `spacing` < `interval_`，残段从根上不存在。

3. **`src/neupan_controller.cpp:217`** —— 重采样后再喂：
   ```cpp
   const double spacing = planner_->config().step_time * ref_speed_base_ * 0.999;
   const auto rs = resampleByArcLength(path, spacing);
   planner_->setInitialPath(neupan_ros::pathMsgToPoints(rs, include_initial_path_direction_));
   ```
   **`* 0.999` 是必需的，不是保险丝**：步长若 ≥ `interval_`，`generateLineCurve` 的 while
   会进入一次并在段末留下亚毫米残点，产生 0.0875 / 0.0001 交替的畸形点距，比不改更糟。

4. **`src/neupan_controller.cpp:222`** —— 日志改为打印 `原 %zu → 重采样 %zu poses`，
   让验收 3 可直接从日志读。

编译：`colcon build --packages-select neupan_cpp_ros`

## 【异议】

**有一条，但不影响方案对错，仍按此做。**

这个改动一旦在实机上编译，hw 的实际速度会从 ~0.20 直接升到 ~0.30（+50%），
因为 hw 中的是同一个根因、同一份代码。实机的安全裕度（`collision_threshold: -1`、`d_min: 0.01`）
是在 0.20 m/s 的实际速度下试出来的，速度提上去后停障距离和 backoff 触发时机都会变。
这不是方案错，是修好之后的正确行为暴露了参数标定的隐含前提。

故本轮按「只改代码、不上实机」执行（见【不做】第 1 条），hw 那轮单独安排、低速起步验证。

方案本身无异议 —— 根因已由 `/neupan_initial_path` 实测输出坐实，改动限于单包两文件、
零新增参数、单 commit 可回滚。
