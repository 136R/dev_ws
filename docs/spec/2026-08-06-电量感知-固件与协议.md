# 电量感知（一）—— 固件 ADC + 0x03 协议帧 + ROS 出口

> 来源：`~/.claude/plans/10-30-m-shimmering-treehouse.md` 的 A0/A1/A2 段（2026-08-06 批准）。
> 后续两卡：`2026-08-06-低电归位-任务层.md`、`2026-08-06-动态障碍主动暂停.md`。

## 【目标】

让 ROS 侧能读到电池电压，为下一卡的「低电自动归位」提供数据源。

本卡的终点是：`ros2 topic echo /battery_raw` 有数据、读数与万用表一致、
**且 100 Hz 里程/IMU 链路完全不受影响**。

背景：项目终点是「真实长期使用」，而当前机器人不知道自己快没电，
跑着跑着停在半路，每次要人找回来插电 —— 「长期自主」字面上不成立。
硬件本来就是现成的，只是固件重构时没接。

## 【事实】

### A 组 —— 本会话亲自验证

1. **PCB 上电池分压电路是现成的**（厂商原始整车代码备份，不参与构建）：
   - `docs/vendor/Inc/main.h:97-98`：`VOLTAGE_Pin = GPIO_PIN_1 / GPIOB`
   - `docs/vendor/Src/stm32f3xx_hal_msp.c:129-130`：`PB1 → ADC3_IN1`、`PB0 → ADC3_IN12`
   - `docs/vendor/Inc/APP/Config.h:52-61`：`VOLTAGE_ADC_CHANNEL=ADC_CHANNEL_1`、
     `CURRENT_ADC_CHANNEL=ADC_CHANNEL_12`、`VOLTAGE_R1=47.0f`、`VOLTAGE_R2=10.0f`、
     `CURRENT_RES=0.01f`、`CURRENT_SCALE=20` → 分压比 5.7，量程 3.3×5.7 = **18.8 V**
   - `docs/vendor/**/Battery.c`：完整读取实现（含 VREFINT 校准、5 点去极值滤波）

2. **当前工程未启用任何 ADC** —— `my_robot_stm32.ioc` 的 `Mcu.IP0..IP11` 只有
   DMA/NVIC/RCC/SPI1/SYS/TIM1/TIM2/TIM4/TIM6/UART4/USART1/USART2，无 ADC。
   （`.ioc:245` 的 `ADC34outputFreq_Value=72000000` 只是 RCC 的时钟计算值，不代表外设已启用。）

3. **器件宏是 `STM32F303xC`** —— `.cproject:44` 的 `<listOptionValue value="STM32F303xC"/>`，
   `Mcu.UserName=STM32F303RBTx`。

4. **⚠️ 厂商的 VREFINT 通道号在本器件上是错的**：
   `docs/vendor/Drivers/STM32F3xx_HAL_Driver/Inc/stm32f3xx_hal_adc_ex.h` 中，
   `STM32F303xC` 命中第 517/526 行 `#if` 开启的块（`#endif` 在 1290 行），该块内：
   ```c
   #define ADC_CHANNEL_VBAT      ADC_CHANNEL_17   // 厂商 Battery.c 实际读的是这个
   #define ADC_CHANNEL_VREFINT   ((uint32_t)ADC_CHANNEL_18)   // 本该读这个
   ```
   而 `ADC_CHANNEL_VREFINT = ADC_CHANNEL_17` 的定义在 1365-1370 行，属于
   `#if defined(STM32F373xC) || defined(STM32F378xx)`（1296 行）—— **与本器件无关**。
   同文件 833-834 行注释确认：VREFINT 在所有 ADC 上可用，但同一时刻只允许一个 ADC 连接它。

5. **协议现状**（`firmware/my_robot_stm32/Core/Inc/app/comm_protocol.h`）：
   帧格式 `[0xAA][0x55][TYPE][LEN][DATA×LEN][XOR]`，小端。
   `0x01` 速度指令 payload 4；`0x02` 反馈 payload **36**
   （left_delta 4 + right_delta 4 + acc_xyz 12 + gyro_xyz 12 + yaw_mdeg 4），
   整帧 = 5+36 = **41**。头文件 `:28` 的注释 `/* 37 bytes */` 是**陈旧注释**。

6. **`firmware/` 整个不在 git 里** —— `.gitignore:32` 有一行 `firmware/`，
   `git check-ignore -v` 确认，`git ls-files firmware/` 返回 0 个文件。

7. **WSL 可直接读写 Windows 工程** `/mnt/d/01_Projects/ROS2/project/move_trash_can/stm32/my_robot_stm32`，
   且两份工程 `diff -rq --exclude=Debug` **只在 `.metadata/`（Windows 侧独有）和
   `.settings/language.settings.xml` 上不同**，其余完全一致。

8. **体积实测**（决定 .gitignore 排除规则）：
   `Core/` 332 K / 44 文件；`Drivers/` **5.8 M** / 81 文件；`Debug/` **37 M** / 173 文件；
   `docs/` 140 K；总计 44 M。

9. **GUI 侧已经配好了话题名** —— `/home/bingda/ros_flutter_gui/gui_app_settings.json`

### B 组 —— 子 agent 核查、已给出处，**实现第一步先复核**

> 这些没有在本会话亲自跑命令确认，出处已具体到文件行号。

16. ros2_controllers 2.52.0 **没有 battery broadcaster**（只有 joint_state / imu /

17. GUI 后端 `backend/src/node/ros2/node_streamer.cpp:479-492` 的 `OnBattery`
    **只转发 `percentage`**（`[0,1]` 则 ×100，否则取整），`voltage` 不过桥；
    Dart 侧 `ws_channel.dart:363` 是 `p > 0 ? p : 旧值` → **发 0 会被静默忽略**。

## 【假设】

1. **电池是 3S 锂电（11.1 V 标称）或 12 V 铅酸。**
   依据是厂商 `Config.h:43` 的 `BATTERY_LOW_VOLTAGE 9.6f` + 18.8 V 量程上限，**但没实测过**。
   ｜ 验法：A1 第一步用万用表量满充电压。
   ｜ **必须先验** —— 它决定 `battery.yaml` 的电压表和下一卡的阈值取值。

2. **PB0/PB1 在当前 `.ioc` 里是空闲的**（未被其他外设占用）。
   ｜ 验法：CubeMX 打开后看 PB1 是否已分配；或 grep `.ioc` 的 `Mcu.Pin*` 列表。
   ｜ 若被占用，整个方案要重新找通道 —— **CubeMX 第一步就会暴露，不用预先验**。

3. **`0x03` 帧不会影响 0x02 的 100 Hz 时序。**
   依据：41+13 = 54 B 在 115200 下约 4.7 ms < 10 ms tick。
   ｜ 验法：A2 验收 ③（10 分钟 100±2 Hz、`No fresh STM32 feedback` 零次）。
   ｜ 不用预先验，验收覆盖。

4. **CubeMX 的 "Keep User Code" 能保住现有手写代码。**
   现有手写代码位于 `main.c` 的 `USER CODE BEGIN 2/WHILE/3` 区内（子 agent 报告，B 组待复核）。
   ｜ 验法：生成后 `git diff`。
   ｜ 这正是本卡把固件纳入 git 的主要动机 —— **不预先验，靠 diff 兜**。

### A1 固件 ADC

**CubeMX 配置（用户操作）** —— 必须从 `Categories → Analog → ADC3` 进，
不能只在 Pinout 视图点 PB1（只设引脚不会生成 `MX_ADC3_Init()` / `adc.c` /
不会取消注释 `HAL_ADC_MODULE_ENABLED`，结果是编译过但 ADC 没配）：

| 位置 | 设置 |
|---|---|
| ADC3 → Mode | 勾 **`IN1`** → Single-ended；**同时勾 `Vrefint Channel`**；**不勾** `IN12`(PB0 电流) |
| Parameter Settings | 12 bits / Right / Scan **Disabled** / Continuous **Disabled** / Discontinuous **Disabled** / DMA Continuous Requests **Disabled** |
| | External Trigger = **Regular Conversion launched by software** |
| | Rank 1 Channel 任选（代码动态切）；**Sampling Time = 601.5 Cycles** |
| NVIC / DMA | 都不开 |
| Code Generator | 确认勾 **"Keep User Code when re-generating"** |

**新增 `Core/{Inc,Src}/app/battery.{h,c}`**，从厂商 `Battery.c` 移植，**四处必须改**：

| 厂商写法 | 改成 | 为什么 |
|---|---|---|
| `ADC_SAMPLETIME_2CYCLES_5` | **`ADC_SAMPLETIME_601CYCLES_5`** | 47k/10k 分压源阻抗约 8.2 kΩ，2.5 周期(~35 ns)采不满采样电容 → 读数系统性偏低且温漂。**这是厂商代码里的真 bug** |
| `usGetADC3Value(ADC_CHANNEL_17)` | **`ADC_CHANNEL_VREFINT` 宏**（本器件 = 18） | 见【事实】4。照抄读到的是 VBAT，校准系数偏约 27%，电压系统性偏低 |
| 5 点有状态滑动去极值滤波 | **无状态**：一次连采 8 次，排序取中间 4 个求平均（~70 µs） | 厂商那个滤波器有 `pusVoltageFilter[i+1]==0` 的初始化 hack，可读性差 |
| `vADCRefInit()` 开机采一次 VREFINT | **每次采样都测 VREFINT** | 跟踪 3.3 V 轨随电池跌落/温度的漂移。每秒多一次转换而已 |
| `fGetCurrent()` / `CURRENT_ADC_CHANNEL` | **v1 全砍** | 对低电归位零贡献；厂商实现里硬编码零点+死区，换板就错 |
| `fDoExternalCalibrate()` / `fErrorScale` / `ucUseErrorScale` | 砍掉运行时 API，改编译期 `#define BATTERY_GAIN_CORR 1.0f` | 万用表标一次即可 |

**补厂商没有的一步**：`battery_init()` 里调
`HAL_ADCEx_Calibration_Start(&hadc3, ADC_SINGLE_ENDED)`（上电一次，约 100 µs）
—— STM32F3 的 ADC 不校准达不到标称精度。

**⚠️ 结构性约束：绝不能在 ISR 里采样。**
`HAL_ADC_PollForConversion(&hadc3, 10)` 最长阻塞 10 ms，而 TIM6 ISR 周期正好 10 ms。
做法：`main.c` 的 `while(1)`（目前基本空转）里加 `HAL_GetTick()` 门控的 500 ms 分支调
`battery_sample()`，写进 `volatile uint16_t g_battery_mv`；
`comm_protocol_tick()`（ISR）**只读**这个缓存值。

**增益标定是两趟**：先以 `BATTERY_GAIN_CORR = 1.0f` 烧一版 → 读数与万用表比 →
算出修正系数改常量 → 再烧一版。这是正常流程，不是返工。

### A2 协议 0x03 + ROS 出口

**新增帧**（不扩 0x02）：
```
COMM_TYPE_BATTERY 0x03, LEN=8, 整帧 13 字节, 2 Hz
voltage_mv u16 | current_ma i16(v1 恒 0) | flags u8 | proto_ver u8 | reserved u16
flags: bit0=voltage_valid  bit1=current_valid  bit2=vrefint_ok
```

选 0x03 而非扩 0x02 的**决定性理由是失效模式**：扩 0x02 后若「固件升了 ROS 没升」，
`parse_feedback` 检 `buf[3] != 36` → 每帧作废 → 0.5 s 后 `read()` 返回 ERROR →
**硬件接口整个挂掉，车彻底不能动**（事实 14）。
新增 0x03 则扫描器逐字节跳过，**0x02 照常解析，里程/IMU 完全不受影响**。

**`proto_ver` 必须真正校验**：git 保证源码可追溯，`proto_ver` 保证
**烧进板子的那个二进制**与当前 ROS 对得上 —— 防的是「改了 ROS 忘了重新烧固件」。
ROS 侧读到不匹配时打 warn 并置 `present=false`，**不得静默接受**。

**固件 TX 冲突的解法**（不要「这 tick 发电池、跳过反馈」）：
1. `comm_protocol_tick()` 加 `static int32_t s_left_acc, s_right_acc`，每 tick 无条件累加，
   **只有 `HAL_UART_Transmit_DMA` 返回 `HAL_OK` 后才清零**
   —— 这同时修掉事实 12 的既有隐患；
2. 电池 tick 时把 `[0x02][0x03]` 拼进**同一个** static TX buffer（41+13 = 54 B，
   115200 下 4.7 ms < 10 ms），**一次 DMA 发完**。零竞争、零跳帧。

**ROS 侧扫描器的正确性修改**（不改会引入新 bug）：
守卫改为 `i + 5 <= stream_fill` → header 匹配后按 `stream[i+2]` 分派帧型 →
**该帧型完整长度未收齐则 `break` 等更多字节，绝不能 `i++`**
（否则会扫掉半截正在接收的 0x02 帧，造成偶发丢帧）→ 只有未知帧型/校验失败才 `i++`。

**出口**：`my_bot_hw` 插件内直接开 `rclcpp` publisher 发 `sensor_msgs/BatteryState`
到 **`/battery_raw`**（只填 `voltage` + `present` + `power_supply_status=UNKNOWN`）。
- 不加 state_interface + 自写 broadcaster：ros2_controllers 无现成 battery broadcaster（事实 16），
  自写要 ~250 行 C++ + plugin.xml + 生命周期，为一个 2 Hz 标量不值。
- **不在 `read()` 里发**：在 `on_configure` 建 node + publisher，由已有的非实时
  `rx_thread_fn`（事实 15）解析到 0x03 时发布。完全不碰 100 Hz 控制回路。
- **`ros2_control_hw.xacro` 和 `hw_controllers.yaml` 都不改**
  （也就不会触发 `on_init` 里 `joints.size()!=2 / sensors.size()!=1` 的严格校验）。

电压→百分比的换算、`/battery_status`、低电逻辑**全部不在本卡**，见下一卡。

## 【异议】

**有两条。第 1 条不影响方案对错，仍按此做；第 2 条影响验收可执行性，需在动手时确认。**

### 1. 固件纳入 git 会让 `Drivers/` 的 5.8 M 进历史（不影响对错，仍按此做）

`Drivers/` 是 ST 官方 HAL 库，本可用「重新生成」代替版本控制。纳入后 `.git` 会长约 5~6 M，
且以后每次 CubeMX 升级 HAL 版本都会产生一次大 diff。

但我仍建议纳入：clone 即可编译，且**这次改动恰恰需要看到 CubeMX 往 `Drivers/` 里
拉了哪些 ADC 文件** —— 那正是「ADC 是否真的被启用」的直接证据。
5.8 M 对本仓库不构成负担。**我仍按纳入执行。**

### 2. ⚠️ 验收 1-1 的「3 个不同 SoC 点」在半小时内做不到（影响可执行性，需你定）

要凑齐 3 个真实的不同电量点，得等电池自然放电几小时。这和 A1「半天完成」冲突。

三种取点方式，**动手时按你手上有什么定**：

| 方式 | 前提 | 说明 |
|---|---|---|
| **可调直流电源代替电池** | 有可调电源 | **最推荐**。直接扫 3 个电压点（如 12.6 / 11.1 / 10.0 V），十分钟测完，还能验证量程边界 |
| 分次测量 | 无可调电源 | 满充测一次 → 跑一段时间测一次 → 更晚再测一次。跨天完成，但不阻塞 A2 |
| 只测 1 点 + 放宽验收 | 都没有 | 验收降级为「满充点 ≤0.15 V」，线性度靠 A2 后续实际使用暴露 |

方案本身无异议 —— 硬件现成、协议改动是纯增量、失效模式已分析清楚、
0x02 热路径的回归判据（2-3 / 2-4 / 2-5）覆盖了最大风险。

## 给下一卡（低电归位）的已知不确定性

**低电阈值大概会落在 10.5~11 V，而那正是 1-1 未验证的区间。** 若误差含偏置项而非纯增益，该区间的方向与大小都未知。

建议：阈值留更保守的余量，或在归位逻辑里加一次「到位后复查电压」。
**若出现归位触发过早/过晚，第一个该查的就是这里** —— 复现方法是用可调电源扫 10 / 11 / 12.6 V 三点，看比值是否恒定。同一线索已写入 `firmware/my_robot_stm32/Core/Inc/app/battery.h` 的注释，不依赖对话记忆。

## 过程中发现并修掉的既有问题（不在原方案内）

1. **`comm_protocol.c` 静默丢里程**：原 `if (tx_busy) return;` 发生在组包之前，该 tick 的 delta 被丢弃而非延后。已改为无条件累加、DMA 成功才清零。
2. **`serial_protocol_check.py` 完全失效**：常量停留在带磁力计的旧布局（44/49），而固件是 36/41 —— 跑起来每帧都判 bad_frame，验收 1-4 原本无法执行。已修正并加 0x03 支持。
3. **陈旧注释**：`COMM_FEEDBACK_FRAME_SIZE` 注释写 37（实为 41）、`comm_protocol_tick` 注释写 50 Hz（实为 100 Hz）。
