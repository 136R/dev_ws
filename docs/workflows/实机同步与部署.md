# 实机同步与部署

> 开发机（WSL / x86_64）↔ 开发板（香橙派 5 Pro / arm64）。

## 结论先行

**同步分两个节奏，不是改一个值推一次：**

- **功能推送**：开发机仿真跑通后 `git push pi main`，落到板子的"收件箱"分支 `incoming`；
  板子想用时 `git merge --autostash incoming`，没提交的调参会自动收起、合并完再放回。
- **调参回流**：板子上调到满意提交一次，开发机 `git pull pi main` 带回来。

走局域网直传（实测 0.8 秒），不绕 GitHub，速度和 rsync 同级，但板子的 git 状态永远说真话。

**不要用 rsync 同步代码。** 它只在取回 git 不跟踪的产物（地图、rosbag）时才用。

## 为什么不是 rsync

rsync 本身没问题 —— 问题是**「rsync 进一个 git 工作区、还排除掉 `.git`」**：

```bash
rsync -avz --exclude='.git/' ...     # 旧文档教的做法
```

排除 `.git` 是对的（不排除更糟），但这造成一个**结构性的谎言**：文件换成了新版本，而板子的
`.git` 还停在旧 commit —— 于是 git 认为「这些文件是你本地改过的」。

**2026-07 实测**：开发板上因此积累出 **51 个"未提交改动"**，其中绝大多数根本不是本地修改，
而是 rsync 拷过去的开发机成果。代价是板子**失去了"可被追问"的能力**：

| 你想问 | git 的回答 |
| --- | --- |
| 板子上有哪些真正的实机调参？ | 不知道，全混在 51 个里 |
| 能 `git pull` 更新吗？ | 不能，一堆冲突 |
| 板子和开发机差在哪？ | `git diff` 出来全是噪声 |
| 回滚到上个能跑的版本？ | 回滚不了，没有历史 |

最后只能整个工作区推倒重来。

> 旧文档写「日常同步用 rsync，阶段完成用 git」，动机合理（快、不绕公网、不用为调试而 commit）。
> **问题在于这两条路会悄悄分叉，而且没有任何东西会告诉你** —— 直到 51 个文件深了才发现。
>
> 下面的 `pi` remote 方案把这三个优点全保住了，同时不产生第二条真相。

## 连接

```bash
ssh orangepi          # ~/.ssh/config 里已配好别名
```

开发板接的是**手机热点**，所以 **IP 会变**。变了就改一行：

```bash
sed -i 's/^\( *HostName \).*/\1<新IP>/' ~/.ssh/config && ssh orangepi hostname
```

板子上查 IP：`hostname -I`

| | 值 |
| --- | --- |
| 用户 | `orangepi`（**不是** `ubuntu`） |
| 主机名 | `orangepi5pro` |
| 密钥 | `~/.ssh/id_ed25519`（已免密） |

> mDNS（`orangepi5pro.local`）走不通：板子没装 avahi，且 WSL2 在 NAT 后面、不在热点的二层网段上。

## 日常同步：两个节奏

**不绕 GitHub，走局域网直传 —— rsync 的速度 + git 的真实性。**
开发机攒到功能做完再推；板子上调参随便改、随便试，攒到满意再提交。

| 节奏 | 什么时候 | 方向 |
| --- | --- | --- |
| ① 功能推送 | 开发机仿真跑通后，一个功能推一次 | 开发机 → 板子 |
| ② 调参回流 | 板子上调到满意，提交一次 | 板子 → 开发机 |

```bash
# ① 功能推送：开发机
git push pi main          # 落到板子的 incoming 分支，板子工作区一个字节都不动
# ① 功能推送：板子想用上新功能时
ssh orangepi 'cd ~/dev_ws && git merge --autostash incoming'

# ② 调参回流
ssh orangepi 'cd ~/dev_ws && git commit -am "hw: 调了 xxx"' && git pull pi main

# 异地备份（照常）
git push origin main
```

推新功能前最好先做一次 ②：这样板子合并 `incoming` 是直接快进，不会多出合并提交。

**只改了 yaml / launch / 文档就不用重编** —— `--symlink-install` 下这些是软链，板子合并后立即生效。
改了 C++ 才需要重编。

### 参数归属：两边不改同一行

| 归谁 | 哪些 |
| --- | --- |
| 板子 | 实机参数的**数值**：`my_bot_nav/config/hw/*`、`hw_controllers.yaml`、`ekf_hw.yaml`、`laser_filters.yaml`、`mapper_params_hw.yaml`（建图 / 定位两份） |
| 开发机 | 代码、sim 参数、launch、BT、文档 |

开发机做新功能要新增实机参数时，**只加新键、给初始值**，不改已有键的值 —— 要改去板子上改。
守住这条，下面的合并冲突基本碰不到。

### 它不会覆盖开发板

开发机推的是板子的 `incoming`（开发机 `remote.pi.push` 配的映射），**不是**板子正在用的 `main`，
所以推送永远推得过去，也永远不碰板子工作区。真正动工作区的只有板子上那句 `git merge --autostash incoming`：

| 合并时板子的状态 | 结果 |
| --- | --- |
| 没有未提交调参 | ✅ 直接更新 |
| 有未提交调参，和新代码不在同一行 | ✅ `Applied autostash.` —— 调参放回原处，仍是未提交状态 |
| 有未提交调参，**和新代码改了同一行** | ⚠️ `Applying autostash resulted in conflicts.` —— 文件里出现 `<<<<<<<` 记号；调参完整存在 `git stash list` 的 `autostash` 里，不会丢 |
| 板子有自己的提交、还没回流 | 生成一个合并提交，不丢东西（下次 ② 带回开发机） |

冲突时：打开文件，留下想要的值，删掉 `<<<<<<<` / `=======` / `>>>>>>>` 三行记号，然后 `git stash drop`。

> 2026-10 用本机临时仓库实测了前三行，以及"先 ② 再 ①→ 板子快进"（git 2.34.1；板子同版本，`--autostash` 要求 ≥ 2.27）。

### 三个要注意的地方

1. **未跟踪文件不受影响**（`~/.maps/`、`build/install/log`、`COLCON_IGNORE`）。只有当合并进来的
   **已跟踪文件**会覆盖一个**未跟踪文件**时，git 才拒绝合并 —— 这正是下面 VS Code 那个坑的同一机制。
2. **submodule 不会自动更新。** 合并后 gitlink 变了要在板子上补一句：
   `git submodule update --init --recursive`
3. **板子停在 `main` 上，在 `main` 上合并 `incoming`。** 不要 checkout `incoming` 去用 —— 它只是收件箱。

### 怎么配的（换机重装时照做）

```bash
# 开发板
ssh orangepi 'cd ~/dev_ws &&
  git config receive.denyCurrentBranch updateInstead &&
  git config submodule.src/gz_ros2_control.ignore untracked'

# 开发机
git remote add pi orangepi:dev_ws
git config remote.pi.push refs/heads/main:refs/heads/incoming   # git push pi main 落到 incoming
```

> 第一条 `updateInstead` 现在只是保险：万一有人显式推 `main:main`，板子有未提交改动时仍会拒绝，不会覆盖。
>
> 第二条 `submodule.*.ignore untracked` 是必需的：板子上 `src/gz_ros2_control/COLCON_IGNORE`
> 是本地文件，会让主仓库的 `git status` 常驻一个假的"脏" —— 不忽略它，就没法一眼看出板子上有没有真调参。

## 编译（开发板）

```bash
ssh orangepi 'cd ~/dev_ws && source /opt/ros/humble/setup.bash &&
  colcon build --symlink-install --cmake-args -DCMAKE_POSITION_INDEPENDENT_CODE=ON'
```

⚠️ **`--cmake-args -DCMAKE_POSITION_INDEPENDENT_CODE=ON` 在 arm64 上是硬要求。** 不加会报：

```
relocation R_AARCH64_ADR_PREL_PG_HI21 against symbol ... which may bind externally
can not be used when making a shared object; recompile with -fPIC
```

`libneupan` 是静态库，要被链进 NeuPAN controller 插件的**动态库**里。x86_64 上侥幸能过，
aarch64 上直接拒绝。详见 [neupan.md](../../src/my_bot_nav/docs/neupan.md)。

## 从零部署开发板（换机 / 重装 / 工作区烂掉）

### ⚠️ 先关掉 VS Code Remote

**这是个真会咬人的坑。** VS Code 的 C/C++ 扩展会持续往 `~/dev_ws/.vscode/` 写
`c_cpp_properties.json`。而本仓库**跟踪 `.vscode/`**。

于是：`rm -rf ~/dev_ws` 之后 VS Code 立刻把那个文件重建出来 → `git clone` 拉完仓库、
准备 checkout 时发现"未跟踪文件挡路" → **拒绝 checkout 并回滚整个工作树**，只留下 `.git`：

```
error: Untracked working tree file '.vscode/c_cpp_properties.json' would be overwritten by merge.
fatal: unable to checkout working tree
warning: Clone succeeded, but checkout failed.
```

**症状很有迷惑性**：clone 看起来"成功"了，`git log` 也正常，但 `src/` 是空的。

已经中招的话不用重新下载，`.git` 是好的：

```bash
cd ~/dev_ws && rm -rf .vscode && git checkout -f main && git submodule update --init --recursive
```

### 步骤

```bash
# 开发板上
cd ~
mv dev_ws dev_ws.old            # 挪走，不删 —— 里面可能有没备份的地图/bag

git clone --recursive https://github.com/136R/dev_ws.git dev_ws
```

⚠️ **`--recursive` 不能漏。** 漏了 `src/neupan_cpp` 是空目录，NeuPAN 插件编译不出来
（`Failed to create controller. Plugin not found`）。补救：`git submodule update --init --recursive`

```bash
# 实机没有 Gazebo，跳过仿真专用包
touch ~/dev_ws/src/gz_ros2_control/COLCON_IGNORE
```

⚠️ 不加这个，`gz_ros2_control` 会因为找不到 `ignition-gazebo6` 而失败，**连带整个 build 中止**。

```bash
cd ~/dev_ws && source /opt/ros/humble/setup.bash
colcon build --symlink-install --cmake-args -DCMAKE_POSITION_INDEPENDENT_CODE=ON
```

**校验**（应全部 ✓）：

```bash
git log --oneline -1                                              # 在 main 上
git submodule status                                              # 两个都有 commit，前面没有 - 或 +
ls src/neupan_cpp/neupan_cpp_ros/src/neupan_controller.cpp        # 插件源码在
ls install/neupan_cpp_ros/lib/libneupan_controller.so             # 插件编出来了
git status --short | wc -l                                        # 0
```

**回滚**：`rm -rf ~/dev_ws && mv ~/dev_ws.old ~/dev_ws`

### 别忘了地图

`~/.maps/` 在 home 下，**不在 dev_ws 里**，所以重装工作区不会动它。但如果 `~/.maps/` 里没有
posegraph，实机 localization 起不来 —— 得先重建一张：

```bash
ros2 launch my_bot_slam slam.launch.py mode:=mapping
# 遥控跑一圈后（app 后端要在跑）
~/dev_ws/src/my_bot_slam/scripts/save_map.sh <地图名>
```

旧工作区里的历史 posegraph 在 `~/dev_ws.old/src/my_bot_slam/config/maps/hw/serialize_map/`。
